# 1. Проблемные места (где заказ может зависнуть):
1. **Shop API → Shop DB**
    * Возможные проблемы: ошибка сохранения заказа, недоступность БД, некорректные данные.

2. **Shop API → S3 (3D файлы)**
    * Возможные проблемы: файл не загрузился, S3 недоступно, нет подтверждения загрузки.

3. **CRM API → Queue (RabbitMQ)**
    * Возможные проблемы: сообщения теряются, очередь перегружена, потребитель RabbitMQ не забирает сообщения.

4. **Queue → CRM API / MES API**
    * Возможные проблемы: сервис не обработал сообщение, тайм-ауты, отказ в обработке.

5. **MES API → MES DB**
    * Возможные проблемы: ошибка записи в БД, долгие запросы.

6. **MES API → Queue (RabbitMQ)**
    * Возможные проблемы: уведомления об изменениях статуса заказа не доходят, сообщения задерживаются.

# 2. Список данных, которые должны попадать в трейсинг:
Для полноты картины будем отслеживать ключевые события в системе:

1. **Генерация уникального trace-id для каждого заказа**
    * Должен передаваться через все сервисы.

2. **Логирование начала и завершения обработки заказа в каждом сервисе**
    * Какие данные:
        - Время получения запроса.
        - Время завершения обработки.
        - Успех/ошибка.
        - Ошибки/исключения.

3. **Фиксация взаимодействий с RabbitMQ**
    * Какие данные:
        - ID сообщения.
        - Время поступления.
        - Время обработки.
        - Подтверждение успешной обработки.

4. **Мониторинг базы данных**
    * Какие данные:
        - Время записи заказа.
        - Ошибки на уровне БД.

5. **События загрузки 3D-файлов в S3**
    * Какие данные:
        - Время загрузки.
        - Ошибки загрузки.
        - Подтверждение успешной загрузки.

# 4. Мотивация

## Почему нужен трейсинг?
Внедрение системы трейсинга позволит:
- **Быстро выявлять зависшие заказы** – отслеживание движения заказа по всем сервисам поможет понять, на каком этапе он "сломался".
- **Сократить время на разбор инцидентов** – детальная информация о прохождении заказа позволит быстрее находить корень проблемы.
- **Снизить потери заказов** – можно будет выявить и устранить проблемы с потерянными сообщениями в RabbitMQ.
- **Улучшить взаимодействие между командами** – разработчики, DevOps и саппорт получат прозрачный инструмент для анализа инцидентов.

## Влияние трейсинга на бизнес и технические метрики
#### Технические метрики:
1. **Среднее время обработки заказа**
    * Трейсинг поможет выявить узкие места и оптимизировать работу сервисов.
2. **Количество потерянных сообщений в RabbitMQ**
    * Можно будет отслеживать потери и настраивать механизмы повторной доставки.
3. **Среднее время отклика API**
    * Позволит оценить влияние производительности сервисов на задержки в обработке заказов.
4. **Процент ошибок (HTTP 5xx, тайм-ауты)**
    * Трейсинг покажет, какие сервисы вызывают наибольшее количество ошибок.

## Бизнес-метрики:
1. **Процент успешно выполненных заказов без задержек**
    * Улучшение клиентского опыта и снижение отказов.
2. **Время на разбор инцидентов**
    * Быстрое выявление причин проблем позволит сократить время простоя системы.
3. **Увеличение конверсии в успешные заказы**
    * Стабильная система приведет к росту доверия клиентов.

# 5. Предлагаемое решение

Для реализации трейсинга предлагается использовать **OpenTelemetry** для сбора трассировок и **Jaeger** для их визуализации. Также потребуется интеграция с **Prometheus** и **Grafana** для сбора и отображения метрик.

## Основные шаги внедрения
1. **Добавление OpenTelemetry SDK в ключевые микросервисы**
    - Shop API, CRM API, MES API – для сбора трассировок о движении заказов.
    - RabbitMQ – для отслеживания прохождения сообщений по очередям.

2. **Обогащение логов контекстной информацией**
    - Логирование ID заказа на всех этапах.
    - Проставление корреляционных идентификаторов в HTTP-запросах и сообщениях RabbitMQ.

3. **Развертывание Jaeger в качестве системы трейсинга**
    - Хранение трассировок заказов в ElasticSearch или ClickHouse для последующего анализа.

4. **Настройка дашбордов в Grafana**
    - Визуализация метрик производительности API, задержек в RabbitMQ и ошибок.

5. **Расширение схемы взаимодействия компонентов**
    - Добавление OpenTelemetry Collector для агрегации трассировок.
    - Внедрение механизма повторной отправки сообщений при сбоях.

# 6. Компромиссы

1. **Ограниченная интеграция с проприетарными системами**  
   Некоторые внешние или устаревшие внутренние системы могут не поддерживать стандартные методы трейсинга (например, OpenTelemetry). Их доработка может потребовать значительных вложений или быть невозможной без вмешательства сторонних вендоров.

2. **Высокая нагрузка на инфраструктуру**  
   Внедрение трейсинга приведет к увеличению объема логов, метрик и трассировок, что может потребовать масштабирования хранилищ данных (например, Prometheus, Elasticsearch) и увеличения вычислительных мощностей.

3. **Дополнительные расходы на хранение данных**  
   Сбор и хранение трассировок потребует дополнительного места в базе данных или в специализированных хранилищах (Jaeger, Tempo). Если объем заказов большой, это может привести к росту затрат на инфраструктуру.

4. **Оверхед на производительность**  
   Внедрение инструментов трейсинга может увеличить задержки в системе, так как на каждом этапе обработки заказа будут выполняться дополнительные операции по логированию и отправке трассировок. Особенно это критично для высоконагруженных API.

5. **Сложность поддержки и обучения команды**  
   Требуется обучение разработчиков, DevOps-инженеров и аналитиков новым инструментам (OpenTelemetry, Jaeger, Grafana). Также возрастет сложность поддержки системы, особенно в случае появления аномалий в данных трассировки.

6. **Необходимость доработки сервисов**  
   Если текущие микросервисы не поддерживают экспорт трассировок, потребуется их модификация. Это может затронуть бизнес-логику и привести к временным задержкам в разработке новых функций.

7. **Низкая ценность для статичных или редко используемых сервисов**  
   Если сервисы обновляются редко или не обрабатывают динамические данные (например, справочники, статические API), трейсинг в них не даст значимой пользы, но создаст дополнительные накладные расходы.

# 7. Аспекты безопасности

1. **Аутентификация и авторизация**
    - Доступ к системе трейсинга получат только сотрудники с корпоративными учетными записями.
    - Использование **SSO (Single Sign-On)** и **OAuth 2.0** для безопасной аутентификации.
    - Роли:
        - **Support** – просмотр трассировок для анализа инцидентов.
        - **Developer** – доступ к деталям трассировки и логам.
        - **Admin** – управление конфигурацией трейсинга.

2. **Шифрование данных**
    - **TLS 1.2+** для передачи данных между сервисами.
    - Хранение трассировок в **шифрованных базах данных** (например, Elasticsearch с включенным TLS).

3. **Ограничение доступа**
    - Доступ к системе трейсинга возможен только из корпоративной сети или через **VPN**.
    - Фильтрация запросов с помощью **WAF (Web Application Firewall)**.

4. **Логирование и мониторинг безопасности**
    - Отслеживание несанкционированных попыток входа.
    - Настройка **SIEM-системы** (например, ELK Stack или Splunk) для анализа логов безопасности.

5. **Защита от утечек данных**
    - Маскирование или удаление конфиденциальных данных в трассировках.
    - Ограничение времени хранения трассировок (например, **14-30 дней**).

6. **DDoS-защита**
    - Ограничение количества запросов (Rate Limiting).
    - Автоматическое отключение подозрительных источников трафика.

# 8. Автоматический мониторинг и алертинг

## 8.1. Реализация автоматического мониторинга
Автоматический мониторинг процесса прохождения заказа будет реализован через интеграцию данных трейсинга с системой мониторинга и логирования. Для этого:
- Данные трейсинга (метки заказов, статусы обработки, время задержек) будут отправляться в **Prometheus** и **Elasticsearch**.
- **Grafana** будет использоваться для построения дашбордов с визуализацией прохождения заказов.
- Настроена корреляция между **трассировками (Jaeger)** и **логами (Elasticsearch)** для быстрого поиска причин зависания заказов.

## 8.2. Реализация алертинга
Для оперативного реагирования на проблемы в обработке заказов будет внедрен **Prometheus Alertmanager**, который будет:
- Отправлять оповещения в **Slack, Telegram, Email** при обнаружении аномалий.
- Включать **автоматические оповещения DevOps и поддержки** при критических сбоях.

**Примеры алертов:**
1. **Заказ завис более чем на 10 минут** в одном из сервисов (Shop API, CRM API, MES API).
2. **Очередь сообщений RabbitMQ перегружена** (более 1000 сообщений в обработке).
3. **Время обработки заказа превысило 5 минут** в среднем за последние 10 минут.
4. **Сервис недоступен более 1 минуты** (HTTP 5xx или отсутствие ответов).
