# Выбор и настройка мониторинга в системе

## 1. Анализ системы в контексте мониторинга

### 1.1. Основные проблемы текущего мониторинга
1. **Неполная картина метрик** – Яндекс Метрика отслеживает только взаимодействие пользователей с веб-сайтом, но не учитывает API-запросы, задержки на стороне бэкенда, состояние очередей сообщений и общую работоспособность системы.
2. **Отсутствие мониторинга API** – Shop API и MES API – критичные компоненты, но их работа не отслеживается, что не позволяет анализировать скорость отклика, количество ошибок и нагрузку.
3. **Нет мониторинга бизнес-процессов** – важно понимать, сколько заказов создаётся, как быстро они обрабатываются, где возникают задержки.
4. **Отсутствие алертов** – система не предупреждает о проблемах (например, рост времени обработки заказа), что затрудняет оперативное реагирование.

### 1.2. Какие системы требуют мониторинга в первую очередь?
✅ **Shop API** – так как именно здесь начинается заказ, важно следить за временем ответа, числом ошибок и зависаниями.  
✅ **MES API** – отвечает за обработку заказов, влияет на скорость работы операторов. Мониторинг поможет выявить узкие места.  
✅ **RabbitMQ (очереди сообщений)** – позволяет понять, нет ли задержек в доставке событий, что важно для уведомлений и изменений статусов заказов.  
✅ **Базы данных (Shop DB, MES DB)** – если база медленно отвечает, вся система будет тормозить.

### 1.3. Метрики, которые нужно отслеживать:
- **Производительность API**: количество запросов, среднее и максимальное время ответа, количество 5xx и 4xx ошибок.
- **Нагрузка на базы данных**: количество запросов, время выполнения, блокировки.
- **RabbitMQ**: число сообщений в очереди, время обработки сообщений.
- **Бизнес-метрики**: количество созданных заказов, время обработки заказа, процент успешно выполненных заказов.
- **Состояние серверов**: загрузка CPU, использование памяти.

## 2. Мотивация

Внедрение мониторинга необходимо для выявления узких мест, предотвращения инцидентов и обеспечения стабильной работы системы. Сейчас данные Яндекс Метрики охватывают только сайт, но не API и внутренние сервисы. Это приводит к ситуации, когда проблемы обнаруживаются только после жалоб пользователей. Систематический мониторинг поможет:
- Уменьшить количество инцидентов за счёт проактивного реагирования.
- Сократить время на устранение проблем благодаря быстрому обнаружению неисправностей.
- Улучшить пользовательский опыт, минимизируя задержки и ошибки.
- Поддерживать высокую производительность API, что особенно важно после открытия системы для сторонних интеграций.

## 3. Выбор подхода к мониторингу

Разные части системы выполняют различные функции, поэтому для каждой из них мы выберем подход, который лучше всего соответствует целям мониторинга.

### 3.1. Shop API и MES API → RED (Rate, Errors, Duration)
Эти API критичны для работы системы, так как они отвечают за размещение и обработку заказов. Подход **RED** поможет отследить их состояние:

- **Rate (Частота запросов)** – сколько запросов поступает в API в секунду. Это важно для понимания нагрузки.
- **Errors (Ошибки)** – процент запросов, заканчивающихся 4xx и 5xx ошибками.
- **Duration (Время обработки)** – среднее и максимальное время ответа API.

Этот подход позволит оперативно реагировать на рост ошибок и увеличенные задержки в API.

### 3.2. Базы данных (Shop DB, MES DB) → USE (Utilization, Saturation, Errors)
Базы данных являются узкими местами системы, поэтому важно отслеживать:

- **Utilization (Утилизация)** – насколько загружена база (CPU, RAM, диск, соединения).
- **Saturation (Насыщение)** – очереди запросов, блокировки транзакций.
- **Errors (Ошибки)** – количество неудачных запросов, таймаутов, deadlock’ов.

Этот подход поможет избежать ситуации, когда база данных перегружена и замедляет работу всей системы.

### 3.3. RabbitMQ (Очереди сообщений) → USE
Очереди сообщений важны для асинхронной коммуникации между сервисами. Подход **USE** будет наиболее эффективным:

- **Utilization** – загрузка очередей, размер буфера.
- **Saturation** – количество сообщений в очереди, время обработки.
- **Errors** – недоставленные сообщения, ошибки потребителей.

Если очередь сообщений начинает наполняться и сообщения задерживаются – это тревожный сигнал о возможных проблемах в системе.

### 3.4. Производительность серверов (Shop API, MES API, БД) → Четыре золотых сигнала
Для инфраструктуры (серверов, контейнеров, балансировщиков) подойдёт классический подход **"Четыре золотых сигнала"**:

- **Latency (Задержка)** – как быстро сервер обрабатывает запросы.
- **Traffic (Трафик)** – объём поступающих запросов.
- **Errors (Ошибки)** – сбои в работе сервисов.
- **Saturation (Насыщенность)** – насколько загружены ресурсы (CPU, память, сеть).

### 3.5. Заключение
Мы используем **RED для API**, **USE для баз данных и очередей сообщений**, **Четыре золотых сигнала для серверов и инфраструктуры**. Этот комбинированный подход обеспечит **глубокий мониторинг всех уровней системы**, позволяя быстро выявлять узкие места и оперативно реагировать на сбои.

Этот комбинированный подход обеспечит **гибкий и полный мониторинг системы**. Если бизнес спросит, зачем это нужно, можно объяснить, что без таких метрик **невозможно прогнозировать сбои и улучшать производительность**. 🚀

## 4. Метрики и их обоснование

### **Выбранные метрики и их описание**

Для каждой части системы выбраны наиболее значимые метрики, позволяющие отслеживать производительность, стабильность и выявлять узкие места.

---

### 4.1. API-сервисы (Shop API, CRM API, MES API)

#### Количество запросов (RPS)
- **Метрики**:
   - `Number of requests (RPS) for internet shop API`
   - `Number of requests (RPS) for CRM API`
   - `Number of requests (RPS) for MES API`
- **Зачем нужна:**  
  Позволяет оценить нагрузку на API-сервисы, выявить аномалии (всплески активности или резкие падения).
- **Ярлыки:**
   - Метод запроса (`GET`, `POST`, `PUT`, `DELETE`)
   - Код ответа (`200`, `400`, `500` и др.)

#### Время отклика (Latency)
- **Метрики**:
   - `Response time (latency) for shop API`
   - `Response time (latency) for CRM API`
   - `Response time (latency) for MES API`
- **Зачем нужна:**  
  Позволяет выявить деградацию API и возможные узкие места.
- **Ярлыки:**
   - Тип запроса (чтение, запись)

#### Ошибки HTTP 500
- **Метрики**:
   - `Number of HTTP 500 for shop API`
   - `Number of HTTP 500 for CRM API`
   - `Number of HTTP 500 for MES API`
- **Зачем нужна:**  
  Позволяет оперативно реагировать на падения API.
- **Ярлыки:**
   - Конечная точка (`/orders`, `/products`, `/users`)

#### Количество одновременных сессий
- **Метрики**:
   - `Number of simultanious sessions for shop API`
   - `Number of simultanious sessions for CRM API`
   - `Number of simultanious sessions for MES API`
- **Зачем нужна:**  
  Позволяет контролировать максимальное число пользователей, находящихся в системе.

---

### **4.2. Базы данных (Shop DB, MES DB)**

#### Использование памяти
- **Метрики**:
   - `Memory Utilisation for shop db instance`
   - `Memory Utilisation for MES db instance`
- **Зачем нужна:**  
  Позволяет отслеживать проблемы с нехваткой памяти.

#### Число активных соединений
- **Метрики**:
   - `Number of connections for shop db instance`
   - `Number of connections for MES db instance`
- **Зачем нужна:**  
  Помогает контролировать число активных соединений и предотвращать перегрузку БД.
- **Ярлыки:**
   - Тип запроса (чтение/запись)

#### Размер базы данных
- **Метрики**:
   - `Size of shop db instance`
   - `Size of MES db instance`
- **Зачем нужна:**  
  Позволяет отслеживать рост объёма данных.

---

### **4.3. Очереди сообщений (RabbitMQ)**

#### Число сообщений в dead-letter queue
- **Метрика**:
   - `Number of dead-letter-exchange letters in RabbitMQ`
- **Зачем нужна:**  
  Указывает на проблемы с обработкой сообщений (ошибки потребителей).

#### **Число сообщений в обработке**
- **Метрика**:
   - `Number of message in flight in RabbitMQ`
- **Зачем нужна:**  
  Позволяет отслеживать нагрузку на очередь сообщений.

---

### **4.4. Инфраструктура (CPU, память, трафик)**

#### Загрузка CPU
- **Метрики**:
   - `CPU % for shop API`
   - `CPU % for CRM API`
   - `CPU % for MES API`
- **Зачем нужна:**  
  Позволяет предотвратить перегрузку сервисов.

#### Использование памяти
- **Метрики**:
   - `Memory Utilisation for shop API`
   - `Memory Utilisation for CRM API`
   - `Memory Utilisation for MES API`
- **Зачем нужна:**  
  Позволяет выявлять утечки памяти.

#### Трафик (входящий и исходящий)
- **Метрики**:
   - `Kb transferred (received) for shop API`
   - `Kb provided (sent) for shop API`
- **Зачем нужна:**  
  Позволяет отслеживать аномалии (DDoS-атаки, перегрузку сети).

---

### **4.5. Дополнительные метрики**
Добавим:
1. **Время обработки заказов** – помогает отслеживать задержки в бизнес-процессах.
2. **Количество успешных заказов (HTTP 200)** – ключевая бизнес-метрика.
3. **Процент ошибок в API** – `Number of HTTP 500 / Number of requests` для отслеживания стабильности системы.

## 5. План действий
1. Развернуть систему мониторинга (например, Prometheus + Grafana).
2. Настроить сбор метрик с API и RabbitMQ.
3. Добавить агрегацию логов (например, ELK Stack или Loki).
4. Реализовать дашборды с ключевыми метриками.
5. Настроить оповещения в случае превышения пороговых значений.


> ## **Драфт технического задания на внедрение мониторинга**
>
>### **1. Развертывание системы сбора и хранения метрик**
>- **Выбрать и развернуть time-series базу данных** (например, **Prometheus** для хранения метрик).
>- **Настроить агрегирование и долгосрочное хранение данных**.
>
>### **2. Настройка агентов сбора данных**
>- **Подключить Prometheus Exporters** для API-сервисов, баз данных и очередей RabbitMQ.
>- **Настроить Node Exporters** на серверах для мониторинга CPU, памяти и дисковой нагрузки.
>- **Настроить Filebeat** для сбора логов и отправки их в **ELK Stack**.
>
>### **3. Настройка мониторинга API и баз данных**
>- **Добавить эндпоинты `/metrics` в Shop API, CRM API, MES API** для сбора метрик.
>- **Настроить сбор метрик запросов (RPS, Latency, HTTP 500 и др.)**.
>- **Подключить метрики состояния баз данных (нагрузка, количество соединений, размер БД)**.
>
>### **4. Настройка мониторинга очередей сообщений (RabbitMQ)**
>- **Подключить Prometheus RabbitMQ Exporter**.
>- **Настроить сбор метрик количества сообщений в dead-letter queue и в обработке**.
>
>### **5. Визуализация данных**
>- **Развернуть и настроить Grafana** для визуализации метрик.
>- **Создать дашборды с ключевыми метриками (нагрузка API, база данных, RabbitMQ, инфраструктура)**.
>
>### **6. Настройка алертинга и автоматических реакций**
>- **Настроить Alertmanager (Prometheus) для отправки уведомлений** (Slack, Telegram, email).
>- **Определить критические пороги метрик** (например, Latency API > 500 мс → оповещение DevOps).
>- **Настроить автоматическое масштабирование API и баз данных** при перегрузках.
>
>### **7. Документирование и обучение команды**
>- **Подготовить документацию по метрикам и их интерпретации**.
>- **Провести обучение для команды DevOps и разработчиков** по использованию дашбордов и реагированию на инциденты.
>

## 6. Определение показателей насыщенности и план действий при их превышении

### 6.1. CPU Utilization (нагрузка на процессор)
- **Пороговое значение:** >80% в течение 5 минут.
- **Почему:** Если процессор загружен более чем на 80% продолжительное время, это может привести к замедлению работы API, задержке в обработке заказов и общей деградации производительности.
- **Действия при превышении:**
   - 📌 **Предупреждающий алерт** при 70% загрузке CPU.
   - 🚨 **Критический алерт при 80%** – автоматическое масштабирование (добавление инстанса API), уведомление DevOps в Slack.
   - ⏳ Если нагрузка не спадает в течение 10 минут – создается тикет в Jira.

### 6.2. Memory Utilization (использование оперативной памяти)
- **Пороговое значение:** >85% в течение 5 минут.
- **Почему:** Высокая загрузка памяти может привести к сбоям сервисов, OOM-kill процессов и деградации производительности.
- **Действия при превышении:**
   - 📌 **Предупреждающий алерт** при 75% загрузке RAM.
   - 🚨 **Критический алерт при 85%** – добавление инстанса или рестарт сервиса, уведомление DevOps.
   - 🔥 При достижении 95% – экстренный рестарт сервиса и создание тикета на разбор утечек памяти.

### 6.3. Количество соединений с базой данных (DB Connections)
- **Пороговое значение:** >90% от максимально доступных соединений.
- **Почему:** База данных может перестать принимать запросы, что приведет к отказу в обработке заказов.
- **Действия при превышении:**
   - 📌 **Предупреждающий алерт** при 75%.
   - 🚨 **Критический алерт при 90%** – анализ активных соединений, автоматическое отключение неактивных коннектов, уведомление DevOps.
   - 🔄 Если нагрузка не снижается, перезапуск соединений и горизонтальное масштабирование базы.

### 6.4. RPS (Requests per Second) для API
- **Пороговое значение:**
   - **Shop API**: >200 RPS
   - **CRM API**: >50 RPS
   - **MES API**: >100 RPS
- **Почему:** Резкий рост числа запросов может указывать на DDoS-атаку, баг в клиентском коде или всплеск пользовательской активности.
- **Действия при превышении:**
   - 📌 **Предупреждающий алерт** при 80% от порога.
   - 🚨 **Критический алерт** – включение rate limiting, анализ логов, уведомление DevOps.
   - 🔒 Если RPS продолжает расти – временное ограничение трафика от подозрительных IP, включение капчи.

### **6.5. Response Time (latency) для API**
- **Пороговое значение:** >500 мс в течение 3 минут.
- **Почему:** Высокая задержка приводит к плохому пользовательскому опыту и возможным отказам клиентов.
- **Действия при превышении:**
   - 📌 **Предупреждающий алерт** при 300 мс.
   - 🚨 **Критический алерт** при 500 мс – проверка логов, автоматическое масштабирование API, уведомление DevOps.
   - 🔄 Если задержка превышает 1 секунду – автоматическое переключение на резервную ноду API.

### **6.6. Dead-letter queue (DLQ) в RabbitMQ**
- **Пороговое значение:** >1000 сообщений в течение 5 минут.
- **Почему:** Слишком много непринятых сообщений может указывать на проблемы с обработкой заказов.
- **Действия при превышении:**
   - 📌 **Предупреждающий алерт** при 500 сообщений.
   - 🚨 **Критический алерт при 1000 сообщений** – проверка сервисов-потребителей, увеличение количества обработчиков.
   - 🛑 Если количество сообщений продолжает расти – автоматический рестарт проблемных сервисов.

### **6.7. Доступное место в базе данных**
- **Пороговое значение:** <10% свободного места.
- **Почему:** Если место в базе заканчивается, запись новых заказов становится невозможной.
- **Действия при превышении:**
   - 📌 **Предупреждающий алерт** при 20%.
   - 🚨 **Критический алерт при 10%** – автоматическая очистка временных данных, уведомление DevOps.
   - 💾 Если доступное место падает ниже 5% – автоматическое расширение диска.
