1. **Узкие места и проблемы**
   - **Долгий расчёт стоимости заказа в MES** (до 30 минут) создаёт задержки в обработке заказов.
   - **Рост нагрузки на систему**: число заказов растёт на 100 ежемесячно, что создаёт дополнительные нагрузки на MES, CRM и Shop API.
   - **Неэффективная работа с API**: открытие API для внешних пользователей увеличило количество заказов, но также привело к росту проблем с задержками.
   - **Очереди заказов**: RabbitMQ обрабатывает сообщения, но увеличившаяся нагрузка может вызывать задержки и перегрузку брокера.
   - **Проблема с дашбордом операторов MES**: даже после введения фильтрации страница загружается медленно, что снижает эффективность работы операторов.
   - **Ограниченная масштабируемость**: каждый сервис работает на одном инстансе, что создаёт точку отказа и снижает отказоустойчивость.
   - **Процесс развертывания**: отсутствие автоматического деплоя в продакшн и долгие задержки релизов из-за QA-блокеров.

2. **Инициативы для устранения проблем**
   - **Ускорение расчёта стоимости заказа**: оптимизация алгоритма расчёта в MES, асинхронное выполнение, кэширование или предварительный расчёт типовых моделей.
   - **Горизонтальное масштабирование сервисов**: настройка автоскейлинга для Shop API, CRM API и MES API.
   - **Оптимизация API**: кеширование результатов расчёта стоимости, ограничение числа запросов, улучшение логирования.
   - **Пересмотр очередей RabbitMQ**: увеличение количества потребителей, разграничение сообщений на приоритетные и второстепенные, внедрение **Backpressure паттерна** для контроля нагрузки.
   - **Рефакторинг дашборда MES**: возможен переход на WebSockets или GraphQL для обновления данных в реальном времени.
   - **Ускорение процессов CI/CD**: внедрение автоматического деплоя в продакшн при прохождении всех тестов.
   - **Выделение read-replica для баз данных**: разгрузка основного инстанса базы.
   - **Обновление архитектуры API**: внедрение rate limiting, анализ нагрузки, возможный переход на GraphQL или gRPC.
   - **Внедрение Circuit Breaker паттерна** в критически важных взаимодействиях между сервисами для повышения отказоустойчивости.
   - **Нанять дополнительного backend-инженера (C#)**: для ускорения оптимизации MES API.

3. **Приоритизация инициатив**
   - **Высокий приоритет (выполнить в ближайшие полгода)**:
      1. **Оптимизация расчёта стоимости заказа в MES** (критическая проблема, вызывающая задержки).
      2. **Масштабирование инфраструктуры** (горизонтальный масштабинг API и выделение read-replica баз данных).
      3. **Оптимизация дашборда MES** (ускорение загрузки заказов для операторов).

   - **Средний приоритет (следующие 6-12 месяцев)**:
      - Улучшение API (кеширование, ограничение запросов, рефакторинг логики).
      - Пересмотр очередей RabbitMQ для более стабильной работы, внедрение Backpressure паттерна.
      - Ускорение CI/CD процессов и автоматизация тестирования.
      - Внедрение Circuit Breaker паттерна для повышения отказоустойчивости.

   - **Низкий приоритет (более года)**:
      - Возможный переход на новые технологии API (GraphQL/gRPC).
      - Дополнительные улучшения отказоустойчивости.

4. **Целевая архитектура через 6 месяцев**
   - Масштабируемая и отказоустойчивая инфраструктура.
   - Оптимизированные API, ускоренный расчёт стоимости.
   - Ускоренные процессы CI/CD и устранённые блокеры QA.
   - Улучшенное взаимодействие операторов с MES через быстрый дашборд.

5. **Выбор трёх инициатив для полугода**
   - **Оптимизация расчёта стоимости в MES** (так как это основная причина задержек и жалоб).
   - **Горизонтальное масштабирование** (устранение узких мест в инфраструктуре).
   - **Рефакторинг дашборда MES** (ускорение работы операторов, снижение нагрузки на backend).
